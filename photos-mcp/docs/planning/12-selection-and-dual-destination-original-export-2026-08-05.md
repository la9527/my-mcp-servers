# 선택 일괄 제어 및 이중 대상 원본 내보내기 계획

- 작성일: 2026-08-05
- 상태: 구현 및 자동·실행 검증 완료
- 대상: `PhotosMcp.app` 결과 갤러리, Apple 사진 앨범 추가, 분류별 원본 내보내기
- 연계 문서: `11-result-reselection-and-apple-album-save-2026-08-05.md`

## 1. 결정

분석 결과에서 사용자가 고른 사진 집합 하나를 기준으로 다음 두 보관 대상을 함께 또는 각각 실행한다.

1. Apple 사진의 기존 앨범 또는 새 앨범에 사진을 추가한다. 이는 사진 파일을 복제하지 않는 앨범 참조 추가다.
2. 사용자가 정한 로컬 디렉터리에 원본 해상도 파일을 분류별로 복사하고, 안전한 파일명과 분석 메타데이터를 함께 남긴다.

결과 갤러리에는 전역 `전체 선택`과 `전체 해제`를 제공한다. 기본 선택은 현재의 `추천` 사진이며, 전역 선택은 현재 필터나 화면에 보이는 카드 수와 관계없이 분석 결과 전체에 적용한다. 별도 버튼인 `현재 필터 선택`은 필요 시 후속 개선으로 추가하되, 전역 선택과 혼동되지 않도록 명확히 구분한다.

원본 해상도는 분석용 미리보기(현재 1024px 계열)를 뜻하지 않는다. Apple 사진에서 확보한 원본 파일을 기준으로 복사하며, 내보내기 과정에서 업스케일하거나 JPEG 재인코딩하지 않는다.

## 2. 사용자 흐름

### 2.1 결과 선택

1. `추천` 상태 사진을 기본으로 선택한다.
2. 사용자는 카드의 체크 상태를 바꾸고, `전체 선택` 또는 `전체 해제`로 결과 전체를 일괄 조정한다.
3. 선택 수는 필터와 관계없이 항상 같은 위치에 `선택한 N장`으로 노출한다.
4. 선택 상태는 run별 review 데이터에 저장한다. 창을 닫거나 다시 열어도 유지되며, 이 단계에서는 Apple 사진과 파일 시스템이 변경되지 않는다.

### 2.2 내보내기 시트

`선택한 N장 내보내기`를 누르면 하나의 시트에서 아래 대상을 독립 체크 항목으로 제공한다.

| 대상 | 사용자 입력 | 실제 동작 |
| --- | --- | --- |
| Apple 사진 앨범 | 기존 앨범 선택 또는 새 앨범명 입력 | 선택한 사진을 앨범에 추가한다. 사진 라이브러리의 원본은 이동하거나 복제하지 않는다. |
| 분류별 원본 폴더 | 최상위 저장 폴더 선택 | 선택한 사진의 원본 파일을 분류 규칙과 파일명 규칙에 따라 복사한다. |

두 대상을 모두 선택하면 같은 사진 집합을 두 곳에 보관한다. 한 대상만 선택하는 것도 가능하다. 시트는 적용 전 대상별 사진 수, 새로 생길 앨범 또는 폴더 수, 이미 존재하는 결과 수, 원본 확보가 필요한 사진 수를 표시한다.

### 2.3 승인과 완료

1. 내보내기 전 mutation plan을 표시하고 명시적 승인을 받는다.
2. 파일 시스템 내보내기를 먼저 수행하고, 성공한 항목만 Apple 사진 앨범 추가로 진행한다.
3. 두 대상은 하나의 원자적 트랜잭션이 아니므로, 한쪽만 실패할 수 있다. 이때 자동 삭제나 앨범 되돌리기는 하지 않는다.
4. 결과 시트에는 대상별 성공, 이미 존재함, 보류, 실패 수와 영수증을 남기고 `미완료 대상만 다시 실행`을 제공한다.

## 3. Apple 사진 앨범 보관

기존 앨범 선택은 이름이 아닌 Apple 사진 앨범 UUID를 기준으로 처리한다. 같은 이름의 앨범이 여러 개일 수 있으므로, 이름만으로 대상 앨범을 추측하면 안 된다.

- `기존 앨범`: 앨범명, 사진 수, 상위 폴더를 보여주되 내부적으로 `target_album_id`를 사용한다.
- `새 앨범`: 이름과 선택적 상위 폴더를 입력한다. 같은 위치의 이름 충돌은 승인 전에 확인하고, 조용히 중복 앨범을 만들지 않는다.
- `재실행`: Apple 사진 추가의 idempotency key와 영수증을 이어 사용해 이미 추가된 사진을 다시 추가하지 않는다.
- `권한`: Apple 사진 자동화 권한과 기존 15분 승인 토큰 정책을 유지한다.

## 4. 분류별 원본 폴더 보관

### 4.1 디렉터리 구조

선택한 최상위 폴더 아래에 결과 상태, 장면 분류, 촬영 월 순서로 만든다.

```text
<선택한-저장-폴더>/
  추천/
    travel/
      2026-04/
        20260425-143022_여행_공원-꽃_추천_Q064_T051_M080_a1b2c3d4.jpg
  검토-필요/
    family/
      2026-04/
        20260425-143105_가족_실내-인물_검토-필요_Q058_T049_M074_e5f6a7b8.heic
```

- 첫 디렉터리는 최종 분류 상태인 `추천` 또는 `검토-필요`다.
- 두 번째 디렉터리는 분석 결과의 장면 분류(`event_type`)다. UI에는 한국어 표시명을 쓰고, 디렉터리 키는 안정적인 내부 분류 키를 기본으로 쓴다.
- 세 번째 디렉터리는 원본 촬영 월이다. 촬영일이 없으면 Apple 사진의 캡처일, 그마저 없으면 원본 파일 수정 시각을 쓰며, 어떤 날짜를 사용했는지는 메타데이터에 기록한다.
- 선택한 사진 중 원본이 아직 로컬에 없으면 다운로드 또는 재준비 상태를 보여주고, 준비가 끝난 뒤 해당 항목만 재개한다.

### 4.2 파일명 규칙

기본 파일명은 아래 구성 요소를 모두 포함한다.

```text
YYYYMMDD-HHMMSS_<장면-분류>_<짧은-내용>_<추천|검토-필요>_Q<종합>_T<기술>_M<의미>_<충돌방지키>.<원본확장자>
```

- 날짜: 원본 촬영 또는 저장 날짜다. 내보낸 시각은 파일명 대신 메타데이터 `ExportedAt`에 남긴다.
- 장면 분류와 짧은 내용: 모델의 긴 문장을 그대로 쓰지 않고, 일반화된 짧은 장면 표현을 24자 이내로 정리한다.
- 점수: `Q`는 종합 점수, `T`는 기술 품질, `M`은 의미 점수다. 3자리 0 채움으로 정렬을 안정화한다.
- 충돌방지키: 내부 식별자에서 만든 짧은 비노출 해시다. Apple 사진 ID, 로컬 경로, 사람 이름을 파일명에 넣지 않는다.
- 안전성: 경로 구분자, 제어 문자, 지나치게 긴 이름을 제거하고 Unicode 정규화를 적용한다. 같은 이름이 생기면 결정적 suffix를 붙인다.

사람 이름, 얼굴 점수, 정확한 위치, GPS, 원본 경로처럼 민감하거나 재식별 위험이 있는 값은 파일명에 포함하지 않는다.

## 5. 이미지 메타데이터와 원본 보존

파일명만으로는 분석 맥락을 잃기 쉬우므로 내보낸 항목에 표준 XMP 태그와 `PhotosMcp` 전용 XMP 네임스페이스를 기록한다.

| 범주 | 저장 값 |
| --- | --- |
| 표준 태그 | `XMP-dc:Subject`에 `PhotosMcp`, 결과 상태, 장면 분류, 사용자가 넣은 비민감 review 태그 |
| 표시 레이블 | `XMP-xmp:Label`에 `추천` 또는 `검토 필요` |
| 설명 | `XMP-dc:Description`에 정제된 짧은 장면 요약 |
| PhotosMcp 메타데이터 | 종합/기술/의미 점수, 클러스터 순위, 선택 상태, 촬영일 출처, 내보낸 시각, 실행 영수증 ID |

다음 값은 기본적으로 새로 쓰지 않는다: 얼굴 좌표와 품질 세부치, 개인 이름, 원본 사진 ID, 로컬 경로, GPS, 원문 전체 설명. 원본에 이미 들어 있던 EXIF는 복사 과정에서 유지하되, 앱이 새 민감 정보를 삽입하지 않는다.

원본 보존에는 두 의미가 있으므로 UI와 구현을 분리한다.

1. `원본 바이트 보존`: 원본 파일을 그대로 복사하고 `.xmp` sidecar에만 분석 메타데이터를 기록한다. RAW, Live Photo 동영상, 지원하지 않는 형식은 이 방식이 기본이다.
2. `메타데이터를 파일에 포함`: JPEG/HEIC 등 안전하게 지원되는 형식의 복사본에 XMP를 기록한다. 픽셀을 재인코딩하지 않지만 파일 바이트는 메타데이터 추가로 달라질 수 있다.

이 두 방식 때문에 metadata가 필요한 결과 내보내기에서는 hard link를 사용하지 않는다. hard link를 수정하면 Apple 사진에서 준비한 원본 inode까지 바뀔 수 있으므로 항상 별도 복사본을 만든다.

ExifTool을 메타데이터 writer로 사용한다. 현재 기본 macOS 도구인 `sips`는 JPEG/HEIC/RAW 전반의 XMP 쓰기를 안전하게 통일하기에 부족하며, Pillow 기반 저장은 포맷과 기존 메타데이터 손실 위험이 있다. ExifTool 실행 파일의 배포·서명·버전 고정은 구현 단계에서 별도 검증한다.

## 6. 구현 범위

### 6.1 결과 선택

1. review 저장소에 대한 batch 선택 API를 추가한다. `전체 선택`과 `전체 해제`는 분석 run의 모든 photo review 상태를 갱신한다.
2. 결과 갤러리 헤더와 하단 action bar에 선택 수, `전체 선택`, `전체 해제`, `선택한 N장 내보내기`를 둔다.
3. 기본 추천 선택과 사용자의 수동 선택을 구분해 표시하되, 내보내기 대상 판단은 최종 `selected=true` 하나만 사용한다.

### 6.2 내보내기 planner와 writer

1. 선택한 review 결과에서 원본 준비 상태, 분류, 점수, 안전한 파일명을 계산하는 read-only preflight를 만든다.
2. `target_album_id` 기반 Apple 앨범 planner와 `target_directory` 기반 원본 export planner를 하나의 parent plan으로 묶는다.
3. 파일 writer는 원본 복사, 충돌 처리, XMP 또는 sidecar 기록, 로컬 manifest와 영수증 생성을 담당한다.
4. Apple 앨범 writer는 기존 approval token/idempotency 경로를 그대로 쓰고, parent receipt에는 각 대상의 개별 상태를 기록한다.

### 6.3 UI와 복구

1. 내보내기 시트에서 Apple 앨범과 로컬 폴더를 각각 켜고 끌 수 있게 한다.
2. 승인 전에는 예상 파일 경로 수와 메타데이터 모드만 보여주며, 개별 사진 경로나 식별자를 화면 로그에 늘어놓지 않는다.
3. 부분 실패 시 `미완료 대상 다시 실행`은 성공한 Apple 앨범 추가나 파일을 중복 수행하지 않는다.

## 7. 검증 기준

- `전체 선택` 뒤 필터를 바꿔도 run의 모든 사진이 선택 상태이며, `전체 해제` 뒤에는 모두 해제된다.
- 선택 상태는 앱 재시작과 결과 창 재진입 뒤에도 유지된다.
- JPEG/HEIC 원본 내보내기는 분석 미리보기보다 큰 원본 해상도를 유지하고, 재인코딩 없이 복사된다.
- RAW와 Live Photo는 원본 바이트 보존 및 sidecar 정책으로 안전하게 보관된다.
- 디렉터리, 파일명, 확장자, 충돌방지키가 분류·날짜·점수 규칙과 일치한다.
- 메타데이터에는 지정한 XMP 태그가 있고, 새 개인 식별 정보나 로컬 경로가 들어가지 않는다.
- 기존 Apple 앨범은 UUID가 일치하는 대상에만 추가되며, 이름이 같은 다른 앨범에는 추가되지 않는다.
- 두 대상 중 하나가 실패해도 다른 대상의 성공 결과와 영수증이 보존되고, 재실행은 미완료 대상만 처리한다.
- Git 문서, 일반 앱 로그, 오류 보고에 개인 사진, 경로, 사진 ID, 메타데이터 전문을 기록하지 않는다.

## 8. 권장 구현 순서

1. 결과 갤러리에 전역 선택/해제와 선택 수 표시를 추가하고 review 상태 영속성을 검증한다.
2. 원본 내보내기 preflight, 분류 폴더, 안전 파일명, 충돌 처리까지 구현한다.
3. ExifTool 기반 XMP writer와 RAW/Live Photo sidecar 정책을 구현하고 형식별 회귀 시험을 한다.
4. Apple 앨범 UUID 선택과 새 앨범 생성 planner를 구현한다.
5. 두 대상을 하나의 승인 시트와 parent receipt로 묶고 부분 실패 재개를 구현한다.
6. 실제 Apple 사진의 소규모 비민감 샘플로 원본 해상도, 앨범 추가, 파일명, XMP, 재실행을 수동 검증한다.

이 순서에서는 파일을 쓰지 않는 선택 UX와 preflight를 먼저 안정화한다. Apple 사진 변경과 원본 복사는 이후에도 항상 사용자 승인과 영수증을 거쳐서만 실행한다.

## 9. 구현 및 검증 결과

2026-08-05 기준으로 본 문서의 핵심 범위를 구현했다.

- 결과 카드별 선택, `전체 선택`, `전체 해제`, 선택 수 표시와 run별 선택 상태 저장을 적용했다.
- `export_selected_bundle` action으로 Apple 사진 앨범, 로컬 분류 폴더 또는 두 대상을 하나의 승인 계획으로 처리한다.
- 승인 계획에 포함된 사진 ID 집합을 실행 시점의 최종 기준으로 사용한다. 승인 뒤 화면 선택 상태가 바뀌어도 다른 사진이 섞이지 않는다.
- 로컬 원본은 copy 방식으로만 저장하며, 분류·촬영월·점수 기반 안전한 이름, XMP sidecar, 실행 영수증별 JSON manifest를 생성한다.
- Apple 사진의 기존 앨범은 UUID로 지정하며, 같은 이름의 다른 폴더 앨범을 이름만으로 재사용하지 않는다.
- 두 대상 중 로컬 저장이 일부만 성공하면 성공한 사진만 Apple 사진 앨범 단계로 넘긴다. 대상별 영수증을 보존하고 완료한 대상은 재실행에서 건너뛴다.
- 앱에서 승인되지 않은 계획, 이미 소비된 승인 토큰, 다른 run·사진 집합·저장 대상·앨범 폴더의 재개 요청은 차단한다.
- 선택 상태 저장 queue가 끝난 뒤에만 승인 계획을 만들며, 결과나 내보내기 세대가 바뀐 오래된 비동기 callback과 승인 모달은 실행하지 않는다.
- 명시적 `embedded` 메타데이터 요청은 ExifTool을 사용할 수 없거나 일부 파일에 쓰지 못하면 완료로 오판하지 않는다.
- 화면 접근성 식별자와 사용자 로그에는 Apple 사진 ID나 원본 경로를 노출하지 않는다.

자동 검증 결과는 `379 passed`다. 여기에는 선택 영속성, 승인 전 실행 차단, 빈 승인 집합 차단, 승인 토큰 동시 소비, 승인 사진 집합 고정, 부분 성공 후 앨범 재조정, 재개 대상·폴더 검증, 앨범 UUID, 같은 이름의 폴더별·최상위 앨범, 원본 바이트 보존, 안전한 파일명, XMP, strict embedded 모드, 영수증별 manifest와 개인정보 비노출 시험이 포함된다.

배포 검증에서는 `PhotosMcp.app`을 새로 빌드하고 코드서명 검증 후 설치 앱을 재기동했다. `/health`는 `status=ok`, `daemon_status=ready`, `background_job_running=false`, `pending_mutation_count=0`을 반환했다. 실제 화면에서 100장 결과, 선택 22장, 전역 선택/해제, 카드별 체크, `선택한 22장 내보내기`, `두 곳 모두 / Apple 사진 앨범 / 로컬 분류 폴더` 선택 시트를 확인했다. 검증 중에는 승인 이후의 실제 Apple 사진 추가나 사용자 폴더 쓰기를 실행하지 않아 기존 사진 보관함과 파일을 변경하지 않았다.

### 9.1 실제 소규모 내보내기 재검증

2026-08-05에 선택 3장으로 실제 로컬 내보내기를 실행했다. 첫 실행에서는 iCloud에만 원본이 있는 2장의 `360×480` Photos derivative가 원본처럼 저장되는 결함을 발견했다. 분석용 이미지와 내보내기 원본 경로를 분리하고, Apple 사진의 원본 파일 크기 또는 원본 해상도와 일치하는 파일만 원본으로 인정하도록 수정했다.

수정한 설치 앱의 승인 화면은 같은 3장에 대해 `원본 준비 완료 1장 · 준비 필요 2장`을 표시했다. 실제 내보내기는 준비된 1장만 저장했고 결과는 `partial`, `failed_count=2`, `missing_count=2`, `retry_available=true`로 기록했다. 저장 파일은 `4032×3024`, 원본 SHA-256과 동일했으며 XMP sidecar 1개와 영수증별 manifest 1개가 생성됐다. XMP와 manifest에서 사용자 절대 경로, 사진 ID, 사람·얼굴·GPS 필드가 새로 노출되지 않는 것도 확인했다.

Apple 사진 앨범 목록 조회는 쓰기용 AppleScript에서 분리해 읽기 전용 Photos DB를 사용하도록 변경했다. 실제 보관함의 앨범 46개를 약 1.6초에 읽었고, 재빌드 앱의 앨범 선택 시트도 약 3초 이내에 표시됐다. 기존의 무기한 `앨범 목록 불러오는 중…` 상태는 재현되지 않았다.

수정 전 검증 폴더 `PhotosMcp-E2E-20260805-211327`에는 원본 1장과 derivative 2장이 함께 있으므로 최종 원본 백업으로 간주하지 않는다. 수정 후 검증 폴더 `PhotosMcp-E2E-Safe-20260805-214638`만 원본 판정 회귀 검증 근거로 사용한다.
