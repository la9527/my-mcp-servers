# 날짜 재분석·작업 기록 의미·Google Picker 수량 무결성 보강

- 작성일: 2026-09-10
- 대상: PhotosMcp macOS 앱, Android 클라이언트, Google Photos Picker 수집 경로
- 배경 실행: `manual-op-a26b9ce436344f36b5d736fc`
- 대상 기간: 2026-09-01 ~ 2026-09-10, Asia/Seoul

## 1. 사용자 기대와 실제 결과

사용자는 PhotosMcp의 분석 기록과 Android Story를 삭제한 뒤 같은 기간을 처음부터 다시 분석하려고 했다. 그러나 실제 실행은 `reanalyze=false`로 등록되어 Google Photos 2장만 분석했고, Apple Photos는 발견한 6장 전부를 기존 처리 사진으로 판단해 분석하지 않았다.

이 결과를 해당 기간 전체 재분석 완료로 간주하면 안 된다.

## 2. 확인된 원인

### 2.1 작업 기록과 사진별 처리 원장은 별도 수명이다

macOS 앱의 기존 `전체 작업 기록 삭제`는 다음 항목을 지웠다.

- 완료·실패·취소·중단 작업
- Mac·Android 통합 작업 표시 기록
- 사용자 액션과 브라우저 미션 기록
- 작업 결과·미리보기와 임시 Google 다운로드

반면 `processed_photo_assets`는 일일 자동화의 중복 분석을 방지하는 영속 원장이므로 보존했다. 확인 시점에는 Apple 103건, Google Photos 305건, 총 408건이 `completed` 상태로 남아 있었다. 2026-09-10 19:23 KST의 작업 기록 정리는 오류 없이 끝났지만 이 원장은 정리 대상이 아니었다.

Android의 `Story 삭제` 역시 Story와 공유 링크만 제거하는 소프트 삭제다. 원본, 추천 사본, 분석 여부, 사진 앨범을 삭제하지 않는다.

### 2.2 새 날짜 작업은 재분석을 요청하지 않았다

Android 날짜 실행 화면은 이전에 `reanalyze=false`를 고정 전송했다. 따라서 Story를 삭제한 뒤 새 날짜 작업을 만들면 기존 사진까지 다시 분석하는 것이 아니라 신규 사진만 찾았다.

백엔드는 이미 `reanalyze=true`를 지원한다.

- Apple: 완료·제출된 기존 UUID도 다시 후보로 포함
- Google: 기존 처리 media item ID를 제외 목록에서 제거
- 공통: PhotosMcp가 결과 앨범에 만든 관리 사본은 계속 제외
- 공통: 화면 캡처 제외 정책 유지

### 2.3 Google의 화면 선택 수와 API 결과 수가 달랐다

최근 미션은 Chrome 접근성 화면에서 250장 선택과 완료 버튼 클릭을 기록했다. 그러나 Picker API가 페이지 조회로 반환한 항목은 2장이었고, `previously_processed_count`는 0이었다. 즉 이 실행의 Google 2장은 기존 처리 원장이 248장을 제외한 결과가 아니다.

기존 구현은 이 수량 차이를 검증하지 않고 2장을 정상 결과로 제출했다. 이 동작은 부분 결과를 전체 완료처럼 보이게 하므로 fail-closed 무결성 게이트가 필요하다.

## 3. 인물 관리 데이터 확인

인물 정보는 분석 작업 DB와 별도인 다음 비공개 저장소에 보관한다.

- `~/.photos-mcp/people/person-identities-private.sqlite3`
- `~/.photos-mcp/people/people-private.json`
- `~/.photos-mcp/people/crops/`

확인 결과 인물 설정은 삭제되지 않았다.

| 항목 | 확인 결과 |
|---|---:|
| 확정 인물 | 3명 |
| 이름 상태 | 3명 모두 `user_confirmed` |
| Story 이름 동의 | owner 3건 허용, family_share 3건 허용 |
| 기존 얼굴 수동 매핑 | 34건 |
| 제외 얼굴 | 3건 |
| 감사 결정 기록 | 9건 |

새 계보 DB의 `face_observations`, `membership_state_versions`, `current_owner_confirmed_memberships`는 현재 0건이다. 이 DB 파일의 최종 수정 시각은 작업 기록 삭제보다 앞선 2026-09-10 07:46 KST이므로, 이번 삭제로 사라진 것이 아니다. 인물 이름·동의·기존 수동 설정은 유지하고 사진별 관측과 연결은 다음 분석에서 생성하는 구조다.

향후 작업 목록 비우기나 날짜 재분석은 위 인물 저장소를 초기화하면 안 된다.

## 4. 적용한 수정

### 4.1 Android 날짜 실행에 재분석 선택 추가

`날짜로 Story 만들기` 화면에 `해당 기간 전체 다시 분석` 체크 항목을 추가했다.

- 해제: 기존 분석 결과를 재사용하고 새 사진만 분석
- 선택: 해당 촬영일 범위의 원본을 기존 분석 여부와 관계없이 다시 분석
- 두 모드 모두 PhotosMcp 관리 사본과 화면 캡처 제외
- 두 모드 모두 수동 Story 작업에서는 자동 앨범을 변경하지 않음
- 옵션 변경 시 이전 미리보기 승인을 무효화하고 다시 미리보도록 함
- 실행 확인 대화상자에 실제 분석 정책을 표시
- Apple 미리보기에 재분석 대상 수를 별도로 표시

Story를 먼저 삭제했더라도 새 날짜 작업에서 같은 범위를 재분석할 수 있다.

### 4.2 macOS 삭제 명칭과 안내 수정

기존 `전체 기록 삭제` 버튼을 `작업 목록 비우기`로 변경했다. 확인 대화상자에는 다음 보존 항목을 명시한다.

- 사진별 기존 분석 여부
- 인물 관리 정보
- 원본 사진
- 추천 보관소와 Story

같은 기간을 처음부터 처리하려면 Android 날짜 실행에서 `해당 기간 전체 다시 분석`을 선택하라고 연결 안내한다. 중복 방지 원장을 무심코 삭제해 매일 같은 사진을 다시 분석하는 상황을 막기 위해, 작업 목록 삭제가 자동화 원장을 초기화하지 않는 현재 안전 정책은 유지한다.

### 4.3 Google Picker 수량 무결성 게이트

Chrome에서 확정한 선택 수를 Google Picker API 소비 단계까지 전달한다. API는 모든 페이지를 수집한 뒤 선택 수와 비교한다.

1. Picker API 전체 페이지 조회
2. Chrome 확정 수와 일치하면 다운로드 진행
3. API 반영 지연 가능성을 고려해 최대 4회, Picker polling 간격 범위에서 재조회
4. 끝까지 다르면 세션을 `failed`로 기록하고 삭제
5. `picker_item_count_mismatch` 오류로 통합 작업에 전달
6. 불완전한 사진을 분석·Story 성공 결과로 확정하지 않음

Android 오류 상세에는 해당 오류의 의미와 재실행 방법을 별도로 표시한다.

## 5. 데이터 수명 정책

| 기능 | 작업 표시 기록 | 사진별 처리 원장 | Story | 인물 DB | 원본 |
|---|---|---|---|---|---|
| 작업 목록 비우기 | 삭제 | 유지 | 유지 | 유지 | 유지 |
| Story 삭제 | 유지 | 유지 | 소프트 삭제 | 유지 | 유지 |
| 신규만 분석 | 새로 생성 | 기존 원장 사용 | 실행별 생성 | 참조 | 읽기 전용 |
| 해당 기간 전체 다시 분석 | 새로 생성 | 제외 판단에 사용하지 않음 | 실행별 생성 | 참조·사진별 관측 갱신 | 읽기 전용 |

전체 원장을 물리적으로 삭제하는 기능을 날짜 재분석의 선행 조건으로 만들지 않는다. 재분석 의도는 명시적 요청 필드로 전달해야 일일 자동화의 중복 방지 정책과 충돌하지 않는다.

## 6. 검증 항목

- `reanalyze=true`가 Android 수동 실행 payload에 반영되는지
- 재분석 선택 변경 후 미리보기가 반드시 다시 필요한지
- Apple 미리보기가 기존 사진을 재분석 대상으로 계산하는지
- Google 작업에서 Chrome 확정 수가 Picker API 소비 계층까지 전달되는지
- API 반환 수가 부족하면 제한된 재조회 후 `picker_item_count_mismatch`로 실패하는지
- 재조회 중 목표 수에 도달하면 정상 소비하는지
- 수량 불일치 상태에서 분석 작업과 성공 Story가 만들어지지 않는지
- 작업 목록 비우기 안내가 처리 원장과 인물 DB 보존을 명시하는지
- 인물 설정과 이름 동의가 변경되지 않는지

## 7. 운영 재검증 순서

1. Android 앱에서 2026-09-01 ~ 2026-09-10을 선택한다.
2. Apple Photos와 Google Photos를 선택한다.
3. `해당 기간 전체 다시 분석`을 켠다.
4. 미리보기에서 Apple의 재분석 수를 확인한다.
5. 작업을 실행한다.
6. Google에서 Chrome 확정 수와 API 수신 수가 일치하는지 확인한다.
7. Google 정상 확인 후 Apple 분석이 시작되는지 확인한다.
8. 결과 Story, 추천 수, 위치·인물 정보와 단일 텔레그램 최종 알림을 확인한다.

Google이 다시 `250 → 2`처럼 다른 수를 반환하면 작업은 성공으로 끝나지 않아야 하며, Android에는 `picker_item_count_mismatch`가 표시되어야 한다.
