# Google Picker 날짜 검색·분할 수집 실검증

- 검증일: 2026-09-11 KST
- 범위: Google Photos Picker 날짜 검색, 정확한 수량 제한, 최종 완료, Picker API 목록, 임시 다운로드, 세션 수명
- 개인정보: 세션 ID, 파일명, 이미지, OAuth 값, 로컬 저장 경로는 기록하지 않음

## 결론

Chrome DevTools MCP를 통한 날짜 검색과 제한형 선택 매크로가 실제 Google 계정에서 서로 다른 단일 날짜 10회와 5일 이동 창 10회를 각각 연속 처리했다. 모든 소량 케이스에서 UI 선택 수와 Picker API가 게시한 항목 수가 일치했고, 사진 바이트를 임시 저장소에 내려받아 파일 존재를 확인했다. 검증 사진은 분석·추천·Story로 보내지 않았으며 케이스 종료 때 원격 Picker 세션과 로컬 lease를 정리했다.

운영과 같은 Android 수동 요청 경로로 250장 선택도 추가 검증했다. UI 전역 선택 수와 Picker API 게시 항목이 정확히 250개로 일치했고, 이미 처리한 250개는 `reanalyze=false` 원장 정책에 따라 재다운로드·재분석하지 않았다. 이번 결과가 입증하는 것은 **최대 1,000장을 허용하는 구조, 날짜별 소량 E2E, 운영 경로 250장 선택/API 수집, 100장 다운로드 묶음 구현**이다. 신규 사진 250장을 한 번에 다운로드·분석했거나 실제 사진 1,000장을 성공 처리했다는 의미는 아니다. 다음 확장 게이트는 신규 100장 다운로드 중단·재개와 충분한 대상이 있을 때 1,000장 선택이다.

## 실환경에서 발견하고 수정한 문제

1. 접근성 snapshot에서 사진 checkbox UID와 날짜는 정확히 읽혔다.
2. `click(uid)`는 성공 응답을 반환했지만 실제 React checkbox 상태가 바뀌지 않아 같은 사진을 반복 클릭했다.
3. 날짜 parser가 개별 사진으로 검증한 정확한 `aria-label` 하나만 누르는 고정 목적 DOM 매크로로 교체했다.
4. 한 번에 하나만 누른 뒤 새 snapshot의 전역 선택 수를 확인해 지연된 상태 갱신이나 이중 토글을 방지했다.
5. 최종 완료 버튼도 UID 성공 응답만 믿지 않고, `완료/Done/추가/Add` 중 활성 버튼이 정확히 하나일 때만 누르는 제한형 매크로로 통일했다.
6. 선택 상태가 세 번 연속 변하지 않으면 무한 반복하지 않고 명시적 오류로 종료한다.
7. Picker 검색이 버튼으로 닫혀 있을 때와 combobox가 열린 상태를 모두 처리한다. 같은 이름의 숨은 검색 버튼·사진 checkbox가 함께 존재하므로 viewport에 보이는 노드만 조작한다.
8. 여러 날짜는 최신일부터 최대 5일씩 먼저 검색한다. 후보 101장 이상 또는 한 날짜 50장 이상인 창만 `daily_dense`로 전환한다.
9. 5일 범위 문자열은 실제 계정에서 검증했지만 공개 Picker API 계약은 아니다. 결과에 범위 밖 촬영일이 보이거나 검색이 안정되지 않으면 일별 exact-date 검색으로 폴백한다.
10. 검색 매크로가 제공되는 정상 화면에서는 원격 Qwen 워크스테이션 준비를 먼저 기다리지 않는다. 화면 구조가 바뀌어 결정형 검색을 사용할 수 없을 때만 모델 기반 복구를 사용한다.
11. 접근성 트리에 다음 사진이 남아 있어도 실제 DOM viewport 밖이면 클릭 응답이 선택 상태를 바꾸지 않았다. 이 경우 같은 항목을 재클릭하지 않고 사진 그리드를 제한형으로 스크롤한 뒤 새 snapshot과 UID를 읽도록 수정했다.

임의 JavaScript 실행을 모델에 허용한 것은 아니다. 소스에 고정된 매크로는 이미 날짜 parser가 승인한 정확한 사진 label과 유일한 완료 버튼만 조작한다.

## 운영 경로 250장 검증

- 요청: Android 수동 실행과 같은 범위 `2026-09-01~2026-09-11`, Google 한도 250장, `reanalyze=false`.
- 선택 흐름: 5일 범위 probe 후 혼잡 구간만 일별 축소. 첫 구간에서 9월 9일→8일→7일, 다음 5일 구간 probe 후 9월 6일→5일 순으로 진행했다.
- 결과: UI 전역 선택 250장, 자동 완료, Picker API 항목 250개가 일치했다. 250장 초과 선택은 없었다.
- 소요: 432.448초.
- 원격 모델: 요청 0회, prompt/completion token 0. 검색 도구가 준비돼 있어 결정형 경로를 바로 사용했다.
- 수집 원장: 250개 모두 기존 처리 항목으로 판정돼 신규 materialized/download/analysis는 0개였다. 이는 다운로드 실패가 아니라 중복 재처리 방지 정책이다.
- 통합 결과: Google MCP 확인 후 Apple gate가 열렸고 Apple 6개도 기존 처리 항목으로 확인했다. 부모 실행은 오류·미완료 없이 `completed`였고 앱 투영은 새 Story가 없어 `completed_empty`였다.

## 자동 테스트

- Picker/Qwen 제어 집중 테스트: 72개 통과. 서로 다른 날짜를 대상으로 같은 다중 화면 계약을 반복하는 12개 parametrized case, 5일 희소/과밀 분기, 검색 버튼/combobox 상태, 원격 준비 생략, AX/DOM viewport 불일치 복구를 포함.
- Picker·다운로드·worker 관련 집중 회귀: PhotosMcp 66개 통과.
- Hermes worker option·시작 실패 전파 집중 회귀: 30개 통과.
- 최종 전체 회귀: PhotosMcp 995개, Hermes 연동 71개 통과.

## 세션과 다운로드 정책

- 선택 목록은 Picker API의 `pageSize=100`과 `nextPageToken`으로 수집한다.
- 다운로드도 최대 100장씩 진행 상황을 기록한다.
- 원격 Picker 세션은 선택 목록을 읽은 즉시 삭제하지 않는다.
- 다운로드가 길어지면 목록을 다시 읽어 60분짜리 임시 URL을 갱신한다.
- 모든 사진 바이트가 내구 저장된 성공 경로에서만 원격 세션을 정리한다.
- 부분 실패에서는 재조회 가능성을 위해 원격 세션을 유지한다. 다만 세션 자체의 `expireTime`과 권한 철회는 별도 제한이다.

## 남은 검증 게이트

1. 신규 사진 실제 100장 다운로드 도중 중단·재개와 진행 checkpoint.
2. 충분한 대상이 있을 때 1,000장 선택/API 수집 확장.
3. 다운로드 도중 프로세스 종료 후 항목별 재개 원장.
4. 날짜 이외 앨범 제목·장소 검색 UX의 실계정 검증.
5. 동일 날짜를 새 Picker 세션으로 나눌 경우 중복 없는 이어선택 근거. 근거가 없으면 세션은 나누지 않고 다운로드·분석만 100장씩 나눈다.
