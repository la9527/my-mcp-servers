# 2026-09-13 Story 브라우저 화면 맞춤 뷰어 복구 검증

## 결과

PC 브라우저에서 Story 사진을 열 때 `1×`인데도 사진이 확대된 것처럼 잘리던 문제를 수정했다. 소유자 Story, 활성 공유 Story, 인물 필터 Story는 같은 뷰어 자산을 사용하므로 모두 동일하게 교정됐다.

## 원인

기존 뷰어는 사진에 `max-width: 100%`와 `max-height: 100%`를 동시에 적용하고 브라우저의 replaced-element 크기 계산에 화면 맞춤을 맡겼다. Chrome 153의 1,440×900 뷰포트에서 실제 사진 stage는 1,440×704였지만 1,536×2,048 세로 사진 요소가 1,440×1,920으로 계산됐다. stage가 overflow를 감추면서 사진 중앙만 보였고, 상단 표시는 사용자 확대를 하지 않았으므로 `1×`로 남았다.

사진을 dialog가 화면에 올라오기 전에 설정하던 순서도 캐시된 이미지의 load 시점에 따라 가용 영역이 0인 상태에서 맞춤 계산이 실행될 수 있는 구조였다.

## 수정

1. dialog를 먼저 `showModal()`로 표시하고 다음 animation frame에서 사진을 연다.
2. 사진 load마다 원본 종횡비와 현재 stage의 너비·높이를 사용해 contain 비율을 직접 계산한다.
3. 계산된 기준 너비·높이를 사진 요소에 명시해 `1×`를 항상 실제 화면 맞춤 상태로 정의한다.
4. 확대와 pan 한계는 이 기준 크기에서 계산하므로 세로·가로 사진 모두 같은 동작을 사용한다.
5. 창 크기 또는 기기 방향이 바뀌면 새 stage에 다시 맞추고 `1×`로 복귀한다.
6. 다음 사진 전환 중 이전 크기의 사진이 잠시 보이지 않도록 loading 전환을 추가했다.
7. 브라우저 캐시가 구형 자산을 재사용하지 않도록 Story CSS/JS 버전을 `v7`로 올렸다.

## 실제 Chrome 검증

운영 설치 앱을 재시작한 뒤 Chrome 153 디버깅 세션에서 실제 41장 Story를 검사했다.

| 검증 항목 | 결과 |
|---|---|
| 1,536×2,048 세로 사진, 1,440×900 화면 | 사진 528×704 / stage 1,440×704, 전체 표시 |
| 2,048×1,536 가로 사진, 1,440×900 화면 | 사진 939×704 / stage 1,440×704, 전체 표시 |
| 휠 확대 | `1.0× → 1.2×`, 정상 |
| 배율 버튼 복귀 | 화면 맞춤 `1×`, 정상 |
| 키보드 오른쪽 이동 | `1 / 41 → 2 / 41`, 정상 |
| 창 크기 1,440×900 → 1,024×768 | 사진 429×572로 재맞춤 |
| 모바일 412×915 | 사진 412×549 / stage 412×719, 전체 표시 |
| 종횡비 보존 | 세로·가로·모바일 모두 통과 |
| Story 자산 | `story.css?v=7`, `story.js?v=7` 확인 |
| Tailnet 운영 URL | HTTPS Story 41장 로드, 세로 사진 528×704 화면 맞춤 확인 |

추가 회귀 테스트는 Story 자산 버전, load 시 contain 계산, dialog 표시 순서, resize 재맞춤 계약을 고정한다.

```text
tests/test_story_sharing.py
18 passed
```

standalone 앱은 재빌드·설치·재기동했으며 `/health`에서 `status=ok`, `daemon_status=ready`, 실행 중 작업 0건을 확인했다. Tailnet 전용 HTTPS 경로도 같은 `v7` 자산을 응답하는 것을 실제 Chrome에서 확인했다.
