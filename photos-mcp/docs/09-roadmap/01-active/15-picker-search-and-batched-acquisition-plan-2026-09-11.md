# Google Photos 검색·분할 수집 개선안

- 작성일: 2026-09-11 KST
- 상태: 1단계 구현·실계정 소량 20회 및 운영 경로 250장 검증 완료. 2단계 항목 원장·중단 재개 확장은 후속 진행.
- 검토: 에이전트 3개(브라우저 제어, 분할 수집·복구, Google 공식 기능 조사)의 독립 검토를 종합.
- 목적: 최대 1,000장·전체 최대 6시간 정책을 유지하면서 선택 부담, 모델 왕복, 중복 수집, 실패 후 재작업을 줄인다.

## 1. 권장 결정

기본은 **최신일부터 5일 검색 창으로 범위 축소 → 후보가 많은 창만 하루 단위로 재검색 → 한 Picker 세션에서 매크로 기반 선택 → 100장 단위 다운로드·분석 → 하나의 통합 추천·Story**이다.

100장마다 Picker를 새로 여는 기능도 배제하지 않는다. 다만 날짜 구간의 완전 소진이나 같은 날짜 내 이어선택을 검증할 수 있을 때만 활성화한다. 새 세션 10회를 단순 반복하면 같은 최근 100장을 반복 선택할 수 있다.

LLM은 최초 검색 전략·화면 적응·예외 복구에 사용하고, 정상적인 화면 관찰·범위 검증·일괄 개별 선택·스크롤 반복은 제한된 코드 도구가 수행한다. Chrome DevTools MCP는 유지한다. 모델에 임의 스크립트 실행 권한을 확대하지 않는다.

## 2. 세 에이전트의 결론

| 관점 | 발견 | 반영 방향 |
|---|---|---|
| 브라우저 제어 | 화면마다 모델 왕복이 반복되며 기존 fallback은 첫 대상 화면만 선택할 수 있음 | 최신 화면 검증을 유지하는 다중 화면 매크로 선택기 |
| 분할·복구 | 단일 Google child에 단일 session/job 연결, 반복 호출 시 조기완료·덮어쓰기 위험 | 선택·항목·분석 batch 원장과 provider 집계 |
| 공식 기능 | Picker 내부 날짜·장소·앨범명 검색 가능, API 사전 필터는 문서화되지 않음 | 검색 지원 UX + 결과 메타데이터 검증, 임의 URL 파라미터 금지 |

## 3. 공식 지원과 자체 자동화의 경계

Picker는 최근 사진부터 시작하며, 내부에서 키워드·날짜·위치·앨범 제목으로 검색할 수 있다. 완료 후 추가 선택에는 새 세션이 필요하다. 검색 문법, 검색 결과 정렬, 전체선택 버튼, 앨범 전체 일괄 승인은 공식 API 계약으로 가정하지 않는다. 검색창을 Chrome MCP로 조작하는 것은 이 프로젝트의 UI 자동화 구현이며 Google의 무인 검색 API가 아니다. [공식 선택 화면 안내](https://developers.google.com/photos/picker/guides/picking-experience)

`PickingConfig`의 공개 선택 옵션은 `maxItemCount`이다. 기본/최대는 2,000개이며 프로젝트는 기존 최대 1,000장을 유지한다. 날짜·앨범·검색어를 사전 주입하는 공개 필드는 없다. 세션 만료는 반환된 `expireTime`을 사용한다. [세션 리소스](https://developers.google.com/photos/picker/reference/rest/v1/sessions)

`mediaItems.list`는 선택 완료 후 사용한다. `pageSize=100`은 응답 페이지 최대 크기이지 Picker 선택 상한이나 다운로드 완료 단위가 아니다. 응답이 100개 미만 또는 빈 페이지여도 `nextPageToken`이 있으면 계속 조회한다. [목록 API](https://developers.google.com/photos/picker/reference/rest/v1/mediaItems/list)

선택 항목의 `id`는 세션 간 유지된다. `createTime`은 업로드 시각이 아니라 미디어 생성 시각이다. 계정/소스와 영속 ID를 결합해 수집 후 중복을 제거하고 날짜는 사용자 시간대로 검증한다. 브라우저 snapshot UID와 이 영속 ID는 서로 다르므로 UI 이어선택이 자동 해결되는 것은 아니다. [미디어 리소스](https://developers.google.com/photos/picker/reference/rest/v1/mediaItems)

다운로드 `baseUrl`은 60분 유효하며 권한 철회 시 더 일찍 만료될 수 있다. 전체 6시간 작업 기한과 분리해야 한다. 첫 100장 분석을 기다리다가 다음 사진 URL이 만료되지 않도록 수집 저장과 분석을 독립 실행한다. 유효한 세션·권한 안에서 목록 재조회로 URL을 다시 확보할 수 있게 세션을 관리하고, 만료·철회 시 재선택 필요를 표시한다. [다운로드 안내](https://developers.google.com/photos/picker/guides/media-items)

Library API의 검색은 현재 앱이 만든 콘텐츠에 한정된다. 사용자의 기존 Google Photos 전체를 날짜 API로 검색하는 대체 수단으로 사용하지 않는다. [Library API 변경](https://developers.google.com/photos/support/updates)

## 4. 사용자에게 제공할 간단한 수단

### 자동 선택 — 기본

- 기간, Google/Apple, 총 장수, 기존 분석 재사용/재분석 설정은 유지한다.
- Google 검색은 날짜 우선, 필요 시 앨범명·장소·키워드를 추가한다.
- 검색은 후보 축소 수단이다. 날짜·유형·관리 출력물 제외는 수집 단계에서 별도로 검증한다.
- 날짜 기준은 촬영/생성일과 업로드·추가일을 혼동하지 않도록 명시한다. 기존 예약 작업의 증분 정책을 검색 추가만으로 바꾸지 않는다.
- 정확한 날짜 검색 표현과 검색 UI는 실제 계정에서 확인 후 활성화한다. 특정 자연어 표현이 항상 정확하다고 약속하지 않는다.

### 직접 선택 — 보조

- 앱/텔레그램에 `Google에서 직접 선택`, `검색어 복사`, `선택 완료 후 자동 처리`를 제공한다.
- 같은 계정으로 로그인한 휴대폰/PC에서 해당 Picker 링크를 열고 날짜나 앨범명을 검색해 선택한다.
- 사용자가 기존 Google Photos에서 직접 정리한 앨범을 검색하는 방법도 제공한다. 앨범 전체 한 번 클릭 선택은 보장하지 않는다.
- 기간 제한 밖의 수동 선택은 조용히 무시하지 않고 제외 장수·이유를 표시한다. 요청 범위를 임의 확장하지 않는다.
- 사람이 Picker를 조작하는 동안 자동 매크로는 해당 세션 제어권을 양보한다.
- 로그인·CAPTCHA·별도 동의가 실제 필요한 경우에만 텔레그램으로 조치를 요청한다.

## 5. 세 가지 분할을 구분

| 단위 | 기본 정책 | 주의 |
|---|---|---|
| 선택 체크포인트 | 한 Picker 안에서 100/200/300장 등 진행 기록 | Done 전에는 다운로드 가능 상태나 영구 완료가 아님 |
| 다운로드·분석 묶음 | 최대 100장씩 저장·재시도·분석 진행 | API 페이지와 1:1 고정하지 않음 |
| Picker 세션 분할 | 날짜 구간/앨범 등 분리가 검증될 때 사용 | 새 세션은 이전 스크롤·선택 위치를 보장하지 않음 |

예: 날짜 A에 80장, 날짜 B에 95장이 있고 각각 전체 범위를 확인했다면 날짜별 세션으로 수집·완료할 수 있다. 날짜 C에 350장이 있으면 C를 100장에서 완료 처리하고 다음 날짜로 넘어가지 않는다. 우선 C를 같은 세션에서 남은 전역 한도까지 선택하고 다운로드를 100/100/100/50장으로 나눈다.

같은 날짜의 새 Picker에서 다음 100장을 고르는 방식은 안정적인 탐색 앵커/정렬/세부 범위를 실증한 뒤 확장한다. 사후 ID 중복 제거는 가능하지만 같은 사진을 반복 고르는 비용이나 미선택 사진 누락을 해결하지 않는다.

## 6. 선택기 수정

초기 검토에서 제안한 도구 개념이며, 2026-09-11에 날짜 검색·선택·완료 매크로의 첫 구현을 반영했다.

1. `open_and_search_picker`: 기본 5일 범위 검색을 수행하고 반환된 모든 촬영일이 범위 안인지 확인. 현재 Picker가 검색 버튼과 입력란 중 어느 상태인지도 함께 처리.
2. `select_until_checkpoint`: 최신 snapshot → 날짜/유형/남은 한도 검증 → 화면 내 대상 개별 클릭 → 전역 선택수 검증 → 스크롤을 묶어 반복.
3. `verify_and_complete`: 안정된 선택수와 허용된 완료 버튼을 확인한 뒤 완료.

기존 날짜·선택 상한·최신 UID·완료 guard는 재사용한다. 화면이 바뀌면 예전 UID를 재사용하지 않는다. 날짜 그룹 전체선택은 구성 항목·장수·범위를 확인할 수 있을 때만 별도 검증 후 고려한다.

검색 결과는 최근순 타임라인과 다를 수 있다. 오래된 사진 하나를 봤다는 이유로 전체 범위를 소진했다고 판단하지 않는다. 최신일부터 5일씩 probe하며 후보 101장 이상 또는 한 날짜 50장 이상이면 그 창만 일별 검색으로 전환한다. 범위 검색은 Picker 공개 API 계약이 아니므로 범위 밖 날짜가 하나라도 보이거나 결과가 안정되지 않으면 정확한 날짜 검색으로 fail-safe 한다. `전체 범위 확인`, `요청 상한 도달`, `일부만 선택`, `사용자 조치 필요`, `실패`를 구분한다.

`max-model-steps`는 사진 수에 비례한 클릭 예산이 아니라 검색·화면 적응·예외 복구에 LLM을 몇 번까지 호출할지 제한하는 안전 예산이다. 정상 날짜 검색과 사진 선택은 결정형 매크로가 수행하므로 사진 1,000장이라고 모델 단계 1,000개가 필요하지 않다. Hermes가 전달하는 값은 PhotosMcp CLI 계약과 같은 최대 128로 제한했다. 사진 수, 다운로드 100장 묶음, 전체 6시간 제한과는 서로 다른 값이다.

결정형 검색 도구(`fill`, `press_key`, 제한형 `evaluate_script`)가 확인되면 원격 모델 준비보다 첫 5일 probe를 우선한다. 정상 화면에서 Linux 워크스테이션을 켜거나 준비 제한시간을 기다리지 않는다. Picker UI가 바뀌어 이 경로를 쓸 수 없을 때 Qwen을 화면 적응·복구 수단으로 사용한다. 접근성 트리의 후보가 실제 viewport 밖이면 같은 UID/label을 반복하지 않고 그리드를 스크롤한 뒤 새 snapshot으로 계속한다.

## 7. 수집·분석·결과 통합

기존 저장소를 확장하되 새로운 거대 프레임워크 도입은 요구하지 않는다.

- 선택 batch: parent/provider/session, 날짜·검색 범위, 시도 번호, UI/API 장수, scope_exhausted, 오류·진행 시각.
- 항목 원장: 영속 ID, 생성 시각, 제외 이유, 다운로드 상태, 로컬 파일 검증, 재시도, 분석 job 연결. 다운로드 전에 기록한다.
- 분석 batch: 항목 집합과 job ID. 현재 세션 전체를 한 job에 묶는 lease를 항목별로 확장한다.
- provider 집계: 복수 batch가 완료·보류·실패인지 모아 부모 상태에 반영한다. 첫 batch 성공을 전체 Google 완료로 처리하지 않는다.
- 세션은 목록을 읽자마자 삭제하지 않고 필요한 다운로드/재조회가 끝난 뒤 정리한다. URL을 영구 데이터처럼 취급하지 않는다.
- 배치마다 특징 추출·분석을 진행하되 최종 유사사진 그룹/추천은 배치 경계를 넘어 통합한다. 연속 촬영 묶음이 100장 경계에서 갈라져 추천이 중복되는 것을 방지한다.
- 같은 사용자 요청의 Google/Apple 결과는 하나의 generation과 통합 Story로 반영한다. 이전 generation의 결과를 섞지 않는다.
- 최초 Google 사진이 실제 API로 확인되고 로컬 저장된 이후 Apple gate를 열 수 있다. 브라우저는 하나만 제어하고 다운로드·분석은 자원 한도 안에서 겹쳐 진행한다.

총 1,000장 예산은 기존 Google/Apple 합산 정책을 유지한다. `선택`, `유효 고유 대상`, `기분석`, `제외`, `다운로드`, `분석`, `추천`, `남은 대상`을 구분하고 미리 확인되지 않은 사진 수를 확정 수량으로 표기하지 않는다. 재분석은 과거 결과 재사용만 해제하며 같은 실행 안에서 같은 사진을 반복 분석하지 않는다.

## 8. 오류·6시간 정책

- 예약/텔레그램/앱의 실행 옵션과 검증을 공유한다. 현재 Hermes의 432/600 step과 CLI 최대128 불일치를 우선 해소한다.
- 시작 단계의 오류도 자식·부모 상태와 최종 알림에 반드시 기록한다. 정상 수집에 진입하기 전 종료를 감시한다.
- 생존 신호와 실제 진행을 분리한다. 선택수/새 화면/다운로드 바이트가 변하지 않는 반복을 제한한다.
- 전체 deadline은 부모 시작부터 6시간이며 batch마다 다시 6시간을 주지 않는다.
- 기한 도달 시 완료분을 보존하고 미다운로드/미분석/미탐색 범위를 분리한다. 로컬에 확보된 사진은 이어 처리하고, 접근권이 만료된 사진은 재선택 필요로 표시한다.
- 최종 성공/부분완료/오류를 통합 알림 한 번으로 전달한다. 중간 진행은 기존 메시지 갱신 등으로 소음을 줄인다.
- 큐는 실패한 실행의 오래된 running 표시 때문에 무기한 막히지 않도록 종료 감시·정합성 점검을 갖춘다.

## 9. 작은 기능 단위 진행 상태

1. **즉시 복구 기반 — 구현:** 실행 옵션 계약을 최대 128로 통일했고 worker 시작 오류를 자식·부모 실행에 기록하도록 연결했다. 운영 큐 정리는 배포 직전 현재 상태를 다시 확인하고 필요한 실행만 대상으로 한다.
2. **쉬운 선택 도구 — 1차 구현·검증:** Picker 검색창에 5일 범위를 먼저 입력하고 날짜별 후보를 집계한다. 희소 창은 범위 전체를 이어 선택하고, 과밀 창은 최신 하루부터 좁힌다. 접근성 UID 클릭이 성공 응답만 주고 실제 체크하지 않는 문제, 숨은 복제 DOM, AX에는 있으나 실제 viewport 밖인 행을 발견해 현재 viewport의 허용 사진만 누르고 필요 시 스크롤 후 새 snapshot을 읽게 했다. 단일 날짜 10회와 5일 이동 창 10회의 선택·완료·API 조회·임시 다운로드가 연속 통과했고, 운영 Android 수동 경로에서도 UI/API 정확히 250개와 250 상한 준수를 확인했다. 결정형 검색이 가능할 때는 원격 Qwen 준비를 생략했다.
3. **중단 복구 — 일부 구현:** 선택 API 목록은 최대 100장 단위로 다운로드하고, 다운로드가 끝날 때까지 원격 Picker 세션을 보존한다. 장시간 처리 중에는 목록을 다시 읽어 임시 URL을 갱신하며, 성공 시에만 원격 세션을 정리한다. 항목별 영속 원장과 프로세스 재시작 후 미완료 다운로드 재개는 후속 범위다.
4. **통합 처리:** 복수 분석 batch·항목 lease·배치 간 최종 추천·통합 Story/알림.
5. **확장:** 250→1,000장 검증 후, 날짜 분할 세션과 동일 날짜 이어선택이 검증된 경우에만 다중 세션 자동화 활성화.

각 단계에서 실제 기능을 사용할 수 있게 전달한다. 1,000장 시험 완료 전까지 모든 기능 제공을 미루지 않는다.

필수 확인은 UI 선택수/API 목록수, 날짜 밖 제외, 동일 날짜 100장 초과, 다운로드 중단 재개, 중복 세션 무진전, 시작 실패 후 다음 큐 진행, 최종 알림/Story 중복 방지이다. 충분한 실제 사진이 없으면 1,000장 실처리 성공으로 보고하지 않는다.

## 11. 이번 단계 검증 결과

- 결정형 다중 화면 선택 시뮬레이션: 서로 다른 날짜 12회 포함 Picker 제어 테스트 28개 통과.
- Google 실계정 단일 날짜: 2026-09-01~10을 요청 1·2·3장으로 교차해 10회 연속 통과. 실제 선택 가능한 수가 요청보다 적은 날짜도 범위를 넓히지 않고 정상 완료했다.
- Google 실계정 적응형 5일 창: 2026-08-28~09-10 사이의 이동 창 10회를 연속 검증했다. 앞 5개 희소 창은 `five_day_range`, 뒤 5개 과밀 창은 `daily_dense`로 자동 분기했고 모든 UI/API/다운로드 수가 일치했다.
- 운영 Android 수동 경로: 2026-09-01~11, Google 한도 250장에서 5일 probe→일별 축소→viewport 스크롤→자동 완료를 거쳐 UI/API 250/250개가 일치했다. 250개 모두 기존 처리 항목이어서 재다운로드·재분석하지 않았고, Google 확인 후 Apple gate도 정상 해제돼 부모가 오류 없이 종료됐다.
- 각 실계정 케이스는 분석기·추천·Story에 제출하지 않는 임시 저장소에서 다운로드 존재만 확인한 뒤 로컬 lease와 Picker 세션을 정리했다.
- 세부 기록: [Google Picker 날짜 검색·분할 수집 실검증](../../08-reports/01-validation/44-google-picker-date-search-batch-validation-2026-09-11.md)

후속 범위는 앨범명 검색 UX, 항목별 영속 원장, 프로세스 재시작 후 재개, 동일 날짜 대량 화면의 100→250→1,000장 확장 검증이다. 충분한 실제 대상이 없는 상태에서 1,000장 실처리 성공으로 간주하지 않는다.
